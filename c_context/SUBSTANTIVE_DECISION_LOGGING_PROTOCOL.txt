================================================================================
SUBSTANTIVE DECISION LOGGING PROTOCOL
Universal Protocol for Transparent Methodological Documentation
================================================================================

VERSION: 1.0
CREATED: 2026-02-13
PURPOSE: Enable rigorous, transparent, and reproducible tracking of substantive
         methodological decisions in any coding project or research workflow.

This protocol can be integrated into any repository by copying this file and
the accompanying Python utility (protocol_logger.py) into your project.

================================================================================
OVERVIEW
================================================================================

This protocol provides a systematic approach to logging SUBSTANTIVE decisions—
those methodological choices that affect reproducibility, transparency, or the
interpretation of your project's results.

KEY PRINCIPLES:
1. Substantive decisions must be logged prospectively (when made, not retroactively)
2. Each decision includes: trigger, evidence, options considered, decision, rationale
3. Decisions are versioned using semantic versioning (major.minor)
4. All decisions are stored in structured JSON format for programmatic access
5. Protocol creates its own isolated directory structure within your repository

BENEFITS:
- Complete audit trail of methodological evolution
- Justification for all substantive choices
- Support for PRISMA-S, CONSORT, or other reporting guidelines
- Reproducibility and transparency for peer review
- Institutional memory across team members and LLM instances

================================================================================
WHAT CONSTITUTES A "SUBSTANTIVE" DECISION?
================================================================================

Log decisions that affect:
✓ Methodology (algorithms, statistical methods, data collection procedures)
✓ Data quality (cleaning rules, deduplication, validation criteria)
✓ Scope (inclusion/exclusion criteria, threshold selection)
✓ Infrastructure (database changes, file organization, schema design)
✓ Analysis approach (metric selection, filtering logic, aggregation methods)

DO NOT log:
✗ Routine bug fixes without methodological impact
✗ Code refactoring that doesn't change logic
✗ UI/formatting changes
✗ Documentation updates (unless protocol documentation)
✗ Dependency version bumps (unless they change behavior)

RULE OF THUMB: If a peer reviewer or future researcher would ask "why did you
do it this way?", log it as a substantive decision.

================================================================================
HOW TO LOG A DECISION (STEP-BY-STEP)
================================================================================

STEP 1: Recognize a substantive decision point
- You encounter a methodological fork in the road
- Multiple reasonable approaches exist
- The choice will affect reproducibility or interpretation

STEP 2: Document the decision context
- What triggered this decision? (problem, finding, observation)
- What evidence supports the need for a decision?
- What are the quantitative metrics or qualitative observations?

STEP 3: Enumerate options
- List 2-5 reasonable options (don't cherry-pick)
- For each option, note pros/cons if helpful
- Include "do nothing" as an option if applicable

STEP 4: Make the decision
- Select one option based on evidence and project goals
- Document WHY this option is superior (rationale)
- Address trade-offs explicitly

STEP 5: Log using protocol_logger.py
- Use the Python function (see code examples below)
- Specify protocol sections affected
- Document implementation details
- Specify version increment type (major or minor)

STEP 6: Verify logging
- Check protocol/decision_log.json updated
- Check protocol/CHANGELOG.md updated (if using)
- Verify version number incremented correctly

================================================================================
WHEN TO USE change_type="major" vs change_type="minor"
================================================================================

MAJOR VERSION INCREMENT (1.X → 2.0):
- Changing primary data sources
- Fundamental algorithm changes (e.g., switching from regression to neural network)
- Complete workflow redesign
- Breaking changes to data schema
- Changes that make previous results non-comparable

MINOR VERSION INCREMENT (1.2 → 1.3):
- Adding new features or variables
- Improving existing algorithms without changing core approach
- Refining thresholds or parameters
- Adding validation steps
- Expanding scope incrementally

RULE: If someone using version 1.2 of your methodology would get substantially
different results with version 2.0, it's a MAJOR change. If results are
comparable but refined, it's a MINOR change.

WORKED EXAMPLE: Complete Decision Flow
================================================================================

SCENARIO: You're building a document classifier and discover that 30% of your
training documents have missing labels.

STEP 1: Recognize the decision point
"I need to decide how to handle missing labels - this affects model training
and reproducibility."

STEP 2: Gather evidence
- Total documents: 10,000
- Missing labels: 3,000 (30%)
- Label distribution in labeled data: Class A (40%), Class B (35%), Class C (25%)
- Document quality: Missing-label documents appear valid (not corrupted)

STEP 3: Enumerate options
A. Exclude missing-label documents (reduce to 7,000 documents)
B. Impute labels using semi-supervised learning
C. Create "Unknown" class for missing labels
D. Manual labeling of all 3,000 documents

STEP 4: Make decision
Selected Option B with constraints.

STEP 5: Log the decision

```python
from utils.protocol_logger import log_decision

decision_id = log_decision(
    stage="Training Data Preparation",
    trigger="Discovered 30% of training documents lack ground-truth labels",
    evidence={
        "total_documents": 10000,
        "missing_labels": 3000,
        "missing_percentage": 30.0,
        "labeled_distribution": {"Class A": 0.40, "Class B": 0.35, "Class C": 0.25},
        "data_quality": "Missing-label documents appear valid (not corrupted)",
        "manual_inspection": "Sample of 100 missing-label docs reviewed - all legitimate documents"
    },
    options=[
        "Option A: Exclude missing-label documents (train on 7,000 only)",
        "Option B: Semi-supervised learning - train initial model on labeled data, pseudo-label high-confidence predictions for missing data, retrain",
        "Option C: Create fourth 'Unknown' class for missing labels",
        "Option D: Manual labeling of all 3,000 documents"
    ],
    decision="Option B - Semi-supervised learning with confidence threshold",
    rationale="Excluding 30% of data (Option A) wastes valuable training data and may introduce bias if missing labels are non-random. Manual labeling (Option D) is resource-prohibitive (estimated 150 hours). 'Unknown' class (Option C) doesn't align with deployment use case. Semi-supervised approach leverages unlabeled data while maintaining quality control via confidence threshold (≥0.90 for pseudo-labeling). Conservative threshold minimizes label noise.",
    protocol_sections=[
        "Section 3: Training Data Preparation",
        "Section 4: Model Training Procedure"
    ],
    implementation={
        "scripts_created": [
            "scripts/semi_supervised_labeling.py",
            "scripts/evaluate_pseudo_labels.py"
        ],
        "procedure": [
            "1. Train initial classifier on 7,000 labeled documents",
            "2. Generate predictions for 3,000 unlabeled documents",
            "3. Pseudo-label documents with prediction confidence ≥0.90",
            "4. Retrain classifier on labeled + pseudo-labeled data",
            "5. Repeat for max 3 iterations or until convergence"
        ],
        "parameters": {
            "confidence_threshold": 0.90,
            "max_iterations": 3,
            "convergence_criterion": "Accuracy change <0.5% between iterations"
        },
        "validation": [
            "Manual review of 100 pseudo-labeled documents",
            "Track pseudo-label accuracy across iterations",
            "Compare final model to baseline (7K only) on held-out test set"
        ],
        "results": "Pseudo-labeling added 1,847 high-confidence labels (61.6% of missing). Final model accuracy: 0.87 vs 0.82 baseline."
    },
    change_type="minor"
)
```

================================================================================
COMMON PATTERNS AND ANTI-PATTERNS
================================================================================

PATTERN: "Options Exhausted, Need New Approach"
Trigger: "Initial approach [X] failed after [Y] attempts. Need alternative."
Evidence: Specific metrics showing failure, attempts made
Options: List alternative approaches (not just variations of failed approach)
Decision: Select fundamentally different approach
Rationale: Why initial approach failed, why new approach addresses root cause

PATTERN: "Threshold Selection"
Trigger: "Need to determine threshold for [metric] to balance [tradeoff]"
Evidence: Threshold sensitivity analysis (performance at multiple values)
Options: Candidate thresholds with pros/cons
Decision: Selected threshold with clear justification
Rationale: How threshold balances competing objectives

PATTERN: "Unexpected Data Quality Issue"
Trigger: "Discovered [X%] of data has [quality issue]"
Evidence: Quantitative scope of issue, examples, impact on downstream analysis
Options: Handling strategies (exclude, impute, flag, manual correction)
Decision: Selected strategy
Rationale: Balance of data retention, quality, and resource constraints

ANTI-PATTERN: Retroactive Logging
❌ "We made several changes last week, let me log them now"
✓ Log decisions when made, while context is fresh

ANTI-PATTERN: Vague Triggers
❌ "Data quality issues"
✓ "15% of records have timestamps in the future (>current date)"

ANTI-PATTERN: Single Option
❌ "We decided to use approach X" (only option listed)
✓ List at least 2-3 reasonable alternatives

ANTI-PATTERN: Missing Rationale
❌ "We chose Option B" (no explanation)
✓ Explain trade-offs, benefits, and why other options were inferior

ANTI-PATTERN: Implementation-only
❌ Logging just lists code changes without methodological context
✓ Focus on WHAT changed and WHY, implementation is secondary

MULTI-PERSON TEAM USAGE
================================================================================

DECISION AUTHORITY:
Establish clear rules for who can log decisions:
- Option A: Any team member can log decisions (review in PR)
- Option B: Only project lead logs decisions
- Option C: Decisions require team consensus before logging

MERGE CONFLICTS:
If two people log decisions simultaneously:
1. Manual merge required in decision_log.json
2. Person with lower decision ID wins (DEC-005 vs DEC-006)
3. Re-number second person's decision and increment version accordingly
4. Document merge in commit message

GIT WORKFLOW:
1. Create feature branch for work requiring decision
2. Log decision in feature branch
3. Submit PR including decision_log.json changes
4. Review focuses on decision rationale
5. Merge to main updates protocol version

BEST PRACTICE: Include decision ID in commit messages
Example: "Implement semi-supervised labeling (DEC-003)"

================================================================================
TROUBLESHOOTING
================================================================================

ISSUE: "Version numbers out of sync"
SOLUTION: Manually edit decision_log.json metadata.protocol_current_version

ISSUE: "Decision ID collision (two DEC-005s)"
SOLUTION: Manually renumber later decision, update references

ISSUE: "CHANGELOG.md not updating"
SOLUTION: Verify file exists at protocol/CHANGELOG.md with [Unreleased] section

ISSUE: "Want to undo a logged decision"
SOLUTION: DO NOT delete. Instead, log a new decision reverting the change:
  - Trigger: "DEC-003 proved infeasible due to [reason]"
  - Decision: "Revert to previous approach from v1.2"
  - This preserves complete history

ISSUE: "Need to log decision after the fact"
SOLUTION: Log with honest trigger:
  - "During implementation, realized [issue] not addressed in planning"
  - Include timestamp when decision was actually made (not logged)
  - Note in rationale: "Logged retroactively on [date]"

================================================================================
FREQUENTLY ASKED QUESTIONS
================================================================================

Q: How detailed should the "evidence" section be?
A: Include enough quantitative data for someone to verify the decision was
   reasonable. Metrics, counts, percentages, specific examples. Avoid vague
   statements.

Q: What if we're exploring and don't know the options yet?
A: Log the decision AFTER exploration, when you have clarity. Document what
   you explored in the "evidence" section.

Q: Do we log decisions during prototyping?
A: Only if the prototype findings inform a substantive decision. Prototype
   iterations themselves don't need logging.

Q: How do we handle gradual drift (many small changes)?
A: When accumulated small changes cross a substantive threshold, log a
   decision documenting the evolution. Example: "After 10 minor adjustments,
   threshold changed from X to Y. Logging as substantive decision."

Q: Can we modify a logged decision?
A: The decision_log.json is append-only. To modify, log a new decision that
   supersedes or refines the previous one. Reference prior decision by ID.

Q: What if we disagree about whether something is substantive?
A: Err on the side of logging. Better to have too much documentation than
   too little. Low-impact decisions can be noted as such in rationale.
